# Informe de Auditoría de Seguridad — ARHIAX RE (Backend FastAPI / Vercel)

**Alcance:** `arhiax-RE/api/*`, `arhiax-RE/public/index.html`, `arhiax-RE/vercel.json`, `arhiax-RE/requirements.txt` y scripts de soporte del repo.
**Fecha de auditoría:** sesión actual.
**Método:** revisión estática de código (lectura directa de archivos, búsquedas transversales). No se ejecutó ningún ataque contra el despliegue.

---

## RESUMEN EJECUTIVO

**Severidad general: CRÍTICA.**

La aplicación está **desplegada en producción sin ningún control de autenticación efectivo**. El "login" es cosmético: la contraseña y el token están hardcodeados en el código fuente (`api/index.py:62,138`), el token estático nunca se valida en el servidor, y **todos los endpoints de datos** (listar/crear/actualizar/eliminar casos, descargar dictámenes PDF, subir archivos) son accesibles de forma anónima. Un atacante puede enumerar y **borrar todos los dictámenes** (`DELETE /api/dictamenes/{id}` con `shutil.rmtree`), descargar PDFs con PII de titulares (nombres y cédulas), y leer el contenido íntegro de la base de datos vía `GET /api/dictamenes`.

A esto se suman: subida de archivos sin validación de contenido ni tamaño (vector DoS y superficie para vulnerabilidades de pypdf), CORS mal configurado (`allow_origins=["*"]` + `allow_credentials=True`), divulgación de tracebacks completos al cliente, ausencia total de encabezados de seguridad (CSP, X-Frame-Options, HSTS), rutas de archivos construidas con input del usuario, PII hardcodeada en el código, y dependencias sin pinning ni lockfile (pypdf con CVE de DoS conocida si la versión es anterior a 3.15).

**Lo que sí está bien:** no se encontró SQL injection explotable (todas las queries usan parámetros `?`), no hay SSRF directo explotable hoy (las URLs externas son fijas), y no hay API keys de terceros expuestas.

**No se encontraron (verificado):**
- **SQL injection explotable** — todas las queries de `api/index.py`, `api/database.py` usan parámetros `?`; único f-string es `api/solar_automation.py:26` con columna interna (F-19).

- **API keys / tokens de terceros** — no hay secretos de servicios externos en el repo.
- **Lectura arbitraria de archivos** — no hay endpoint que lea un path controlado por el usuario; `pdf_path` se genera en servidor.

## PRIORIDADES DE REMEDIACIÓN (Top 5)

1. **Autenticación y autorización reales en toda la API** (F-01, F-02, F-05, F-22): sesiones o JWT con expiración verificados en cada endpoint; eliminar `ACCESS_PASSWORD` y el token estático; mover secretos a variables de entorno de Vercel; prohibir acceso anónimo a listar/descargar/actualizar/eliminar casos (IDOR).
2. **Protección de subidas y rate limiting** (F-03, F-04, F-12): límite de tamaño, validación de contenido real (magic bytes/MIME), parseo de PDFs aislado con timeout y pypdf ≥3.15; rate limit en `/api/login` y en endpoints pesados (geocodificación, compilación, Playwright).
3. **Corregir CORS y añadir encabezados de seguridad** (F-06, F-10): lista blanca de orígenes sin `*` + credentials; CSP, `X-Frame-Options`, HSTS, `X-Content-Type-Options`, `Referrer-Policy` en `vercel.json`.
4. **Eliminar la divulgación de información interna** (F-07, F-13, F-14, F-17): no devolver tracebacks ni rutas internas al cliente; sanitizar `folio_matricula` antes de usarlo en rutas/headers (F-08); retirar PII (cédulas) y rutas absolutas del código; corregir los claims falsos de integración IGAC/geoportal (F-21).
5. **Endurecer la cadena de dependencias y el almacenamiento** (F-16, F-20): pinning exacto + lockfile, actualizar pypdf a versión parcheada, escaneo de vulnerabilidades en CI; sacar `database.db` del repo y migrar a una BD persistente gestionada; unificar la ruta de BD entre módulos (F-19, F-20).
